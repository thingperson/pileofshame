## The drift, in detail

**`components/GamePassBrowse.tsx:264–286` — `handleAddAndPlay` promotes to Playing Now with no cap check.**

```
// components/GamePassBrowse.tsx:281
status: 'playing',
```

- The handler calls `addGame({ ..., status: 'playing' })` directly. `GamePassBrowse.tsx:10` imports **only** `TIME_TIER_CONFIG` from `lib/constants` — `MAX_PLAYING_NOW` is never imported, and there is no `nowPlayingCount` guard anywhere in the file.
- **It's live and reachable.** Mounted at `app/page.tsx:1025`; the button is `GamePassBrowse.tsx:640` (the "Sub Shuffle" add-and-play CTA), and the modal is also openable from Reroll (`Reroll.tsx:44`).
- **Every other promotion path is guarded** — `Reroll.tsx:222`, `JustFiveMinutes.tsx:118`, `GameCard.tsx:426`, `GameCard.tsx:567` (`handlePlayAgain`), `app/page.tsx:319`. All five block the 4th with the same toast. `lib/store.ts:289` (`playAgain`) writes `'playing'` without an internal cap, but its only call site (`GameCard.tsx:571`) guards it, so that one is fine.
- **This is exactly what the locked entry forbids.** DECISIONS 2026-04-06 (L1597), *How to apply this*: "If a new flow lets a user mark a game as Playing Now, it must go through the same cap check. **No direct state writes.**" The entry's own rejected-alternatives list names "Enforce the cap in one place" as rejected precisely because "users can enter Playing Now from six different UI flows."
- **No superseding DECISIONS entry** authorizes a Game Pass exception → ❌ unauthorized, not ⚠️.
- **Severity: low-moderate.** Functionally the user can push Playing Now to 4+ through Sub Shuffle, which is the exact shelf-drift the cap exists to prevent. Not a crash, not a data-loss bug — a psychology-guardrail leak.
- **Suggested fix (Brady's call — not applied):** import `MAX_PLAYING_NOW` in `GamePassBrowse.tsx` and add the same `nowPlayingCount >= MAX_PLAYING_NOW` early-return + toast used at `Reroll.tsx:222`, before the `addGame` call at L272.

**Why the assertion nearly missed it.** `decision-playing-now-cap-3`'s surface list (rewritten 2026-08-02) enumerates `Reroll.tsx`, `JustFiveMinutes.tsx`, `GameCard.tsx` — `GamePassBrowse.tsx` isn't on it. Grepping only the listed surfaces would have returned a clean pass. This is the **third consecutive time** an incomplete surface list nearly hid a real drift (JFM omission caught 07-20/07-29, `constants.ts` omission caught 07-20). The fix that keeps working is running the check repo-wide and treating the surface list as a hint, not a boundary.

## Violation of a LOCKED entry that has no assertion

**PSN import auto-assigns Completed from trophy progress.**

```
// components/PSNImportModal.tsx:108
status: game.progress === 100 ? 'played' : 'buried',
```

- DECISIONS 2026-05-20 (L1777), the file's **only explicitly `**LOCKED.**`-tagged entry** (L1783): *"never auto-assign Completed, Up Next, or Moved On from heuristics. Imports default to Backlog. Period."* It names the two prior rollbacks — **Xbox achievements** and **Steam HLTB inference** — and calls itself "the third time this pattern has been caught."
- Xbox and Steam are both clean today: `XboxImportModal.tsx:128` and `SteamImportModal.tsx:261` hardcode `status: 'buried'`. **PSN was never swept.** PSN trophy progress is the same class of external-completion signal as Xbox achievements — the exact substitution the lock was written to stop.
- Live: `PSNImportModal` is mounted via `ImportHub.tsx:111`.
- This is the **fourth instance** of a pattern the canon says was rolled back three times. It sits in the highest-value assertion gap, flagged as a "should add" in the 07-19, 07-20, and 07-29 audits and never added — which is precisely why it went unseen.
- **Suggested fix (Brady's call — not applied):** `PSNImportModal.tsx:108` → `status: 'buried',`. (The `timeTier` heuristic on L107 is a separate field, not covered by the lock — leave it.)

**🔍 Related, needs a human ruling — Playnite CSV import.** `PlayniteImportModal.tsx:196` calls `mapStatus()` (L34–40), which maps Playnite's `completionStatus` to `played` / `playing` / `bailed`. This is **user-declared** state the user typed into Playnite, not a heuristic inferred from data signals — meaningfully different from achievement percentages. A strict read of "Imports default to Backlog. Period." forbids it; the entry's *rationale* ("the user decides when something is done, not us") arguably permits it, since the user did decide. **Can't tell — needs Brady's call.** Whichever way it goes, the ruling should be written into DECISIONS so the future assertion knows what to allow.
